# 能不能让 Cat 一边睡一边还活着？—— 一次真机实验

状态：完成（2026-07-27，AWS i4i.metal）。这是机制验证，**不是生产 SLA**。

## 1. 为什么做这个实验

Cats 现在让一个 Cat "睡下去"的办法是：把虚拟机暂停，然后把它的内存页从物理内存里踢出去，
写到本地硬盘上。这个办法省内存非常有效，但有个副作用——**虚拟机被暂停了，里面的程序就
完全不动了**。时钟不走，定时任务不触发，token 不刷新，连接断开。

对用户来说这意味着什么：假如你有一个 Java 服务，里面写了"每 10 分钟同步一次订单"，
Cat 睡下去之后这个任务就再也不跑了。要让它继续工作，你得改代码——把定时任务从程序里
搬出来，交给平台去触发。这个改造成本是很多用户不愿意付的。

于是有了这个想法：**能不能不暂停虚拟机，让程序继续跑着，但把它用不到的内存收回来？**
如果能做到，用户就得到一个"定时任务照跑、代码一行不改、又比全速运行便宜得多"的档位。
本实验里把这个假想的档位叫 **Dozing（打盹）**。

这个实验就是去测：**打盹能省多少内存？值不值得做成一个产品档位？**

## 2. 一句话答案

**不值得。**

一台 1 GiB 内存的 Cat，跑一个空闲的 Spring Boot 服务，宿主机上实际占用 612 MB。
打盹用尽今天所有可用手段，最好能压到 345 MB——**省了 44%**。
而现有的"暂停+踢出内存"在同一台机器上把它压到了 **0.11 MB，省了 99.98%**。

差距不是"再调调参数就能追上"的量级，是两个数量级。打盹省下的那 44% 还要付出代价：
每秒数千次的内存换页（累计四百多万次），以及定时任务的触发时间开始飘 ±10 秒。

所以结论反过来了：**不要造一个"让时钟继续走"的新状态，而应该去解决"暂停之后时钟停了"
这个问题本身**——让控制面记住"10:10 要干活"，到点把 Cat 叫醒。现有的睡眠机制已经把内存
省到了极致，剩下要搬走的只是"谁在 10:10 醒着"这一件事。

## 3. 怎么测的

### 测试环境

一台 AWS i4i.metal 裸金属机（128 核，1 TB 内存，本地 NVMe 固态盘），跑 Cloud Hypervisor v53。

**关键一点：虚拟机用的是 Cats 自己的镜像**（`deploy/metal/build-guest-image.sh` 产出的那个），
不是随便找的 Ubuntu 云镜像。这很重要，因为：

- Cats 镜像的**虚拟机内核就是宿主机内核**（6.17），所以本实验依赖的几个内核特性不用猜有没有，
  也不存在"实验用的内核跟生产不一样"这种免责声明。
- Cats 镜像里 1 号进程是轻量的 `cats-init`，不是 systemd + snapd + cloud-init 那一大套。
  用云镜像量出来的内存地板会被一堆用户根本不会跑的东西垫高，那个数字是假的。

### 测试负载

一个真的 Spring Boot 3.3.5 服务（web + actuator），里面有两个定时任务：一个
`@Scheduled(fixedRate = 120000)`（每 2 分钟），一个 `@Scheduled(cron = ...)`。
每次触发都同时记下墙上时钟和程序内部的单调时钟，这样就能看出定时器到底准不准。

堆设成 `-Xms64m -Xmx384m`。这里有个教训：第一轮我图省事写成 `-Xms384m -Xmx384m`，
结果 JVM 一启动就把 384 MB 堆全部占满并且再也不还，量出来的"地板"其实是我自己那个启动参数
造成的，不是机制的极限。改成小 Xms + 允许堆收缩之后数字才有意义。

### 试了哪些手段

从"什么都不做"开始，一层层往上加，每加一层量一次。每一层都是独立开机、预热（跑 256 MB
堆分配、发 50 次请求、把文件缓存读满）、静置 90 秒，然后才施加手段，再采样 6 分钟。

## 4. 结果：一层层加下来省了多少

"宿主机占用"指的是宿主机上真正被这台虚拟机的内存占掉的物理内存。

| 试的手段 | 宿主机占用 | 省了 | 代价 |
|---|---|---|---|
| 什么都不做（正常运行） | 612 MB | — | — |
| 让虚拟机主动上报空闲页 | 630 MB | **没省，反而涨了** | 无 |
| 上报 + 让虚拟机丢掉文件缓存 | 510 MB | 17% | 无 |
| 再加上虚拟机内的 swap | 518 MB | 15% | 无 |
| 宿主机侧强行回收（不问虚拟机） | 374 MB | 39% | **570 万次换页，虚拟机卡到答不上 HTTP 请求** |
| 全套：swap + 虚拟机内施压 + 宿主机回收 | 404 MB | 34% | **423 万次换页，定时器飘 ±10 秒** |
| 上一行 + 把上报粒度从 2 MB 调成 4 KB | **345 MB** | **44%** | 同上 |
| **现有机制：暂停 + 踢出内存** | **0.11 MB** | **99.98%** | 时钟停走，定时任务不触发 |

最后一行是在同一次运行里量的对照，不是引用别处的数字：暂停前 624 MB，踢完之后 0.11 MB。

一个有意思的中间态：全套手段跑下来，**虚拟机内部确实腾出来了**——JVM 自己的内存占用从
300 MB 降到 119 MB，虚拟机里显示有 729 MB 空闲。但**宿主机侧还是握着 404 MB 不放**。
虚拟机以为自己很空，宿主机却没拿回来。这就是打盹的核心困境，下面第 6 节解释为什么。

## 5. 好消息：定时任务真的照跑

这是打盹这个想法唯一被证实的好处。每次定时任务触发的实际间隔（标称 2 分钟 = 120000 毫秒）：

| 配置 | 实际间隔范围 |
|---|---|
| 什么都不做 | 119 990 – 120 000 毫秒 |
| 只做虚拟机侧的回收（上报、丢缓存、swap） | 119 981 – 120 000 毫秒 |
| **一旦加上宿主机侧强行回收** | **111 388 – 130 515 毫秒** |

也就是说：**只要回收动作是"问过虚拟机"的，定时器精度基本没损失（误差 20 毫秒）。
一旦宿主机开始不问虚拟机就抢内存，定时器就开始飘，最多早/晚 10 秒。**

而且同一批次里，被宿主机强行回收的虚拟机连一个 3 秒超时的 HTTP 请求都响应不了——
有一档甚至连日志文件都取不回来。所以"程序还活着"这句话在重度回收下是打折扣的。

## 6. 为什么打盹省不下来：五个具体障碍

这五条都是实验过程中撞出来的，每一条都是 Cats 可以直接动手的具体事项。

### 6.1 虚拟机主动上报空闲页，对已经跑起来的服务几乎没用

Linux 有个机制叫 free page reporting：虚拟机告诉宿主机"这些页我不用了"，宿主机就把它们
真正释放掉。我先确认了这条路是通的——Cloud Hypervisor v53 支持，虚拟机侧也确实启用了
（内核日志明确打印 `Free page reporting enabled`），而且宿主机收到上报后会真的在硬盘文件上
"打洞"，内存和硬盘空间一起回收。

**但它只能归还"已经在空闲列表上"的页。** 一个跑了一会儿的服务，它的内存早就全变成文件缓存
和堆内存了，空闲列表上没什么东西可报。所以这一档量出来是 0 效果（甚至因为服务还在继续分配
而略涨）。

这个零结果是**真实结论而不是配置错误**——我专门验证了特性协商位和内核日志才敢这么说。

### 6.2 Cats 的虚拟机镜像没有挂 cgroup2

要让虚拟机自己判断"哪些页是冷的"（这是准确性的唯一来源，宿主机只能瞎猜），得对虚拟机里的
进程施加内存压力。Linux 施压的接口在 cgroup 里。

而 `cats-init` 只挂了 proc、sysfs、devpts 和几个 tmpfs，**没有挂 cgroup2**。
所以所有施压命令写下去都静默失败了——我第一轮的"虚拟机内施压"档位数字其实全是假的，
只有 `drop_caches`（丢文件缓存）那一步真正起了作用。

### 6.3 把已经在跑的进程"搬进" cgroup 是没用的

发现没挂 cgroup2 之后我改成先挂载、再把 JVM 进程移进一个新 cgroup、然后施压。还是没效果。

原因是 cgroup v2 的一个基本行为：**进程搬家的时候，它已经占用的内存不跟着搬。**
JVM 进了新 cgroup，但那 210 MB 内存还记在原来的账上，所以对新 cgroup 施压等于对着空气施压
（`memory.current` 只有 256 KB 就是证据）。

**用户的程序必须从启动那一刻就在 cgroup 里。** 这正好解释了 Sprites 为什么要把用户代码
跑在一个 inner container 里——那个设计顺带就把这件事解决了。

改成启动即入组之后，同一套施压脚本立刻见效：虚拟机内堆内存从 213 MB 压到 60 MB，
文件缓存从 229 MB 压到 24 MB，空闲内存涨到 799 MB。

### 6.4 对以堆内存为主的进程施压却不给 swap，会把程序冻死

改对之后我先测了"施压但不开 swap"这一档，结果虚拟机直接卡死——90 秒都返回不了一个请求，
这一档跑失败了。

原因很直白：堆内存（匿名页）没有 swap 就无处可去，内核回收不了，于是 `memory.high` 的
节流机制一直踩着刹车不放。**必须先开 swap 再施压。**

### 6.5 上报粒度默认是 2 MB，碎片化之后就报不出去

这是最后一块拼图。全套手段跑完，虚拟机里空出 729 MB，宿主机还握着 428 MB。为什么？

因为上报机制默认只上报**连续 2 MB 以上的空闲块**（`page_reporting_order=9`）。经过一轮
重度回收和 swap 之后，虚拟机的空闲内存是碎片化的，凑不出连续 2 MB，就报不出去。

我把这个参数改成 0（允许上报 4 KB 的单页）验证了这个猜测：宿主机占用从 428 MB 降到
345 MB，瞬间最低到过 300 MB。**猜测成立，但只解释了一部分**——省下 83 MB，地板还是 345 MB。

### 6.6 顺便：虚拟机内核没有出问题

长时间跑最深的配置，虚拟机内核日志里没有 soft lockup、没有卡死的任务、没有 RCU stall。
只有宿主机强行回收那一档出现了 `workqueue: vmstat_shepherd hogged CPU` 的抱怨——
那是宿主机抢内存造成的，不是虚拟机侧施压造成的。所以这条路**不会把虚拟机搞坏**，
它只是省不下来。

## 7. 一个附带结论：我之前关于 CPU 的说法是错的

实验前我判断 KVM 的 halt-polling（虚拟机空闲时宿主机会先忙等一小会儿，赌中断马上到）
会白烧宿主机 CPU、污染按用量计费的账单，建议关掉。**实测不成立。**

| halt-polling | 虚拟机唤醒频率 | 烧掉多少 CPU |
|---|---|---|
| 默认开启 | 空闲的 JVM | 一个核的 0.65% |
| 关闭 | 空闲的 JVM | 一个核的 0.57% |
| 默认开启 | 每秒 1000 次 | 一个核的 4.81% |
| 关闭 | 每秒 1000 次 | 一个核的 4.93% |

差值在噪声里，每秒 1000 次唤醒时关掉反而略高。6.17 内核的自适应收缩逻辑已经把这个代价
消掉了，**不需要为 Cats 单独去关它**。

顺带拿到两个有用的数：一个空闲的 Java 服务虚拟机大约烧**一个核的 0.65%**；唤醒频率拉到
每秒 1000 次也才 **4.8%**。这印证了"CPU 不用限、按实际用量计费+超卖就行"这个判断——
CPU 在这件事上确实不是瓶颈，内存才是。

## 8. 这次没测到 / 测得不干净的部分

读上面结论之前请先看这一节。

- **块设备走的不是生产路径。** 实验用了普通的 virtio-blk 读文件，生产按 ADR-0015 走
  `cats-blockd` 的 vhost-user-blk。差别在于 vhost-user 会让 blockd 成为虚拟机内存的
  **第二个映射者**，它和"打洞"、"踢出内存"这些动作怎么互相影响，**完全没测**。
  这是最该补的一项——结论有可能因此变化。
- **只测了一台机器、一种规格**（1 GiB 内存 / 2 核 / 堆 384 MB）、一种负载。而且内存地板
  会随**配置的**内存总量变大（内核管理页表的开销正比于配置量而非使用量），所以不能把
  1 GiB 的结论外推到 4 GiB 的 Cat。
- **有三个档位按设计没跑完**（原因就是 6.4 那个冻死问题）。表里"全套"那一行的数字来自
  长跑档位，它施加的是同一组手段。
- **虚拟机里"下一个定时器还有多久到期"的分布没测到。** 采样脚本读到了内核文件但正则没匹配上
  这个内核的格式，275 个样本全是空值。所以之前讨论过的"读虚拟机的下一个定时器时刻、
  然后按时叫醒它"这条路，**本轮没有数据**。
- **暂停之后时钟到底怎么走，这次没测。** 本轮只量了暂停能省多少内存，没量暂停/恢复之后
  单调时钟是不是停走、定时任务会迟多久、`fixedRate` 会不会补跑一堆。我之前在讨论里说过
  "单调钟停走会导致永久漂移"——**这个说法仍然未经验证**。
- 静置 90 秒可能不够让 JVM 完全进入稳态。

## 9. 建议

**别做打盹。** 最好省 44%，需要同时做四件事（镜像挂 cgroup2、用户进程启动即入组、
开虚拟机内 swap、上报粒度调到 4 KB），还要接受几百万次换页；而现有机制省 99.98%。
花同样的工程量去做另一件事回报高得多。

**打盹唯一真实的价值是兼容性**——纯虚拟机侧回收下定时任务精度是 20 毫秒误差，确实做到了
"代码一行不改、定时任务照跑"。但为此要付一个正常运行的 Cat 大约三分之一的内存钱，
这个价格很难卖给用户。

**该做的是把力气放到反方向**：让控制面持有定时任务的时刻表，到点唤醒 Cat
（就是之前讨论里的 `cats schedule` + 导入 crontab + 各框架的适配层）。
内存这一块现有机制已经做到极致了，剩下要解决的只是"谁在 10:10 是醒着的"。

如果还要继续验证打盹，按价值排序：

1. **在生产的 vhost-user-blk 路径上重测**"什么都不做"和"全套"两档。第二个内存映射者
   可能让结论完全变样，这是最大的未知。
2. 把"上报粒度 4 KB"和"虚拟机内施压"组合起来做一次干净的对照。本轮的粒度扫描是在长跑
   之后补做的，不是干净实验。
3. **去量暂停之后的定时器语义**（单调钟停不停、恢复后迟多久、`fixedRate` 会不会补跑一串）。
   这个直接决定 `cats schedule` 的"错过补偿"策略该怎么定，价值比继续救打盹大。

## 10. 怎么复现

```bash
sudo ./run.sh setup      # 装依赖、下 CH v53、构建 Cats 虚拟机镜像和 Spring Boot 探针
sudo ./run.sh ladder     # 第 4 节前六档 + 暂停对照
sudo ./run.sh ladder3    # 启动即入 cgroup 的施压档（注意 6.4：必须先开 swap）
sudo ./run.sh haltpoll   # 第 7 节的 halt-polling 扫描
sudo ./run.sh fprorder   # 第 6.5 节的上报粒度 2MB → 4KB
sudo SOAK_S=600 ./run.sh soak
```

原始数据都在 [`results/`](results/)：每档一个 `raw/<档位>.csv`（每 5 秒一个采样点）、
`raw/<档位>-fires.csv`（每次定时任务触发的两个时钟读数）、`raw/<档位>-guest-mem.txt`、
`raw/<档位>-guest-dmesg.txt`，加上 `host-facts.txt`（机器和内核信息）、
`suspended-reference.txt`（暂停对照）、`guest-pressure.log`（虚拟机内施压的完整过程）、
`raw/haltpoll.csv`、`raw/fpr-order.csv`。
