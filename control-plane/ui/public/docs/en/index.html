Product model

A Cat is a long-lived Linux microVM with a required RootDisk. Compute may stop while the Cat name and durable disk remain. A Workspace is the user-visible authorization and resource boundary; the V1 HTTP API keeps the compatible project path segment underneath.

  • RootDisk follows the Cat and is deleted with it.
  • PersistentDisk is independent, grow-only in V1, and read-write attached to at most one Cat.
  • Endpoint maps a stable hostname to one Guest port and may wake a sleeping Cat.
  • Operation records every asynchronous mutation and its final structured error.

What you will hit today

Cats is moving quickly. These are the boundaries you will actually run into:

CapabilityWhere it stands
Endpoint protocolsHTTP/1.1, with HTTPS terminated at the regional edge. Inbound WebSocket is not supported yet.
Guest outbound networkEvery Cat gets its own network and outbound access, with sensitive destinations blocked. Private Guest-to-Guest networking across nodes is not offered yet.
PersistentDiskRead-write on one Cat at a time, and it can grow but not shrink.
SnapshotsYou can create one; convenience commands to list and restore are not there yet — use the HTTP API.
Wake concurrencyA node caps how many Cats wake at once. Beyond that, wakes queue instead of failing, so a wake can be slower at peak.
Interactive terminalcats shell needs the CLI. The console runs one command at a time, with no persistent terminal.
Performance numbers are evidence, not an SLA

Every performance number we publish carries its sample count, hardware and measurement boundary. Prototype measurements never become production commitments — judge them against your own workload.

Documentation conventions

Examples use the Workspace selected by cats login and a Cat named dev. Replace them for your deployment. Sizes accept binary suffixes such as 512MiB and 8GiB.
