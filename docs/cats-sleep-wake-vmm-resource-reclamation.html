Cats 睡眠、唤醒与 VMM 资源回收

本文说明 Cat 从 Running 进入 Suspend 或 Cold 时，Cloud Hypervisor、cat-agent、cats-blockd 和 Host Linux 分别做什么；Guest RAM 如何从物理内存换出到本地 NVMe；哪些资源能够真正回收；唤醒时如何恢复，以及 Host 故障时如何降级。

1. 最终结论

Cats 不应只有一种“睡眠”。一个机制无法同时满足保留进程、快速唤醒、跨 Host 和彻底释放资源。正确做法是把 Suspend 与 Cold 作为两个不同产品状态。

Suspend：保留 VMM，回收 CPU 和大部分物理 RAM

VMM、KVM fd、设备后端、tap、Attachment lease 和本地 NVMe backing 继续存在。Guest 进程状态保留，必须在原 Host 上 resume。

Cold：退出 VMM，释放全部运行时资源

CPU、RAM、VMM、tap、设备进程和强制本地缓存全部释放。只保留远端 RootDisk/PersistentDisk 与控制面 metadata，之后在任意 Host fresh boot。

VMM 只负责协调暂停，不负责完整资源回收

Cloud Hypervisor 停 vCPU、保存时钟、暂停设备并维护 VM 状态。Guest sync、磁盘 FLUSH、RAM page-out、NVMe 清理和路由变更由平台组件完成。

自动策略：Running → Suspended → Warm → Cold

工作归零后立即 Suspended；稳定 10 分钟后默认转 Warm，Warm 稳定 24 小时后默认转 Cold。计时持久化，Shell/流量触发单次 Wake。

一句话：Suspend 是“机器还在，只是 CPU 停了，RAM 被放到本地 NVMe”；Cold 是“机器没了，只剩远端磁盘，下次重新开机”。
重要限制：Suspend 不是跨 Host 持久状态。原 Host 永久损坏后，内存 backing file 一起丢失；平台必须丢弃进程状态，改用远端 RootDisk 做 Cold Recovery。

2. 三个主要状态

状态进程内存Host 绑定恢复方式适用时长
Running保留且驻留是无需恢复正在使用
Suspended保留在本地内存 backing；多数页不驻留是resume，工作集按需 fault分钟到较短小时级
Cold不保留否新 VMM 从远端 RootDisk 启动长期闲置

3. Running 时 Host 上有哪些资源

理解“回收了什么”，必须先明确运行时实际存在的对象。VMM 只是其中一个进程，磁盘 backend、网络和本地文件同样会占用资源。

VMM 不是全部：即使 VMM 已经暂停，cats-blockd、NVMe memory file、tap、lease 和 Node 路由仍可能存在。资源回收必须由一个跨组件 lifecycle transaction 完成，不能只观察 Cloud Hypervisor 状态。

4. Running → Suspended 的完整流程

Suspend 的正确顺序是“停止新活动 → Guest 落盘 → 本地持久水位 → VMM pause → RAM page-out”。Suspend 是 Host-bound；Warm/Cold/Snapshot/Detach/迁移才必须强制推进到远端水位。

1. 工作与状态门禁

平台与 Guest 工作租约必须为空。Node 关闭 exec/proxy gate，Guest Agent 以 sequence fence 原子关闭 /run/cats/runtime.sock 的新 acquire/renew；任一新工作拒绝本次 Suspend 并恢复 Running。

2. Guest Quiesce

Guest Agent 对 RootDisk/PersistentDisk 执行 syncfs；应用 hook 有严格 deadline。

3. Local durability barrier

cats-blockd 记录 local durable generation；Strict 同时已远端 durable，Relaxed 可在 Suspended 后继续后台 publish。

4. VMM Pause

Cloud Hypervisor 暂停 vCPU、保存时钟、暂停设备并进入 Paused。

5. Memory Page-out

cat-agent 对 Guest RAM mmap 执行 MADV_PAGEOUT，把大部分物理页写回/丢弃。

6. 资源记账

释放 vCPU run budget；更新 resident_bytes、NVMe backing bytes 和 resume commitment。

7. 发布状态

Cat=Suspended；Endpoint 按 wake_policy 返回唤醒响应或触发 Wake。

4.1 为什么先 sync/FLUSH

Guest Page Cache

应用的 write 可能只修改 Guest Linux Page Cache。VMM pause 不会替 Guest 调用 sync，也不会让 ext4 自动产生 FLUSH。

  • 先通过 Guest Agent 调用 syncfs
  • 等待 virtio-blk 请求完成
  • 普通未 fsync 写仍遵循 volatile cache 语义

Host Block Cache

Strict FLUSH 要求远端 Root；Relaxed 只承诺本地 immutable pack。Suspend 可记录本地水位；越过 Host 所有权边界前必须 drain。

  • Pending Commit Pack 固定提交输入
  • 始终 remote generation ≤ local generation
  • 只有 R == L 才允许 Warm/Cold/Snapshot/Detach/迁移
fsfreeze 不是普通 Suspend 的必需步骤：syncfs + 完成 FLUSH 后再 pause 已能形成一致运行状态。fsfreeze 更适合需要把文件系统与磁盘 Snapshot 精确对齐的场景；冻结后必须有 watchdog 保证 unfreeze。

6. Guest RAM 如何从物理内存回收到 NVMe

推荐每个 Cat 使用受控的 file-backed memory zone。Guest 看见的内存大小不变；Host 可以在暂停后回收其物理页，并在恢复访问时从本地 NVMe 按需读回。

6.1 Linux 实际行为

页面类型MADV_PAGEOUT 行为结果

file-backed clean page直接从 page cache 回收下次访问从 backing file fault 回来
anonymous page如果 Host 配置 swap，可换出没有 swap 或不适用时可能不回收

8. Suspended → Running 的唤醒过程

唤醒分为控制面激活、容量准入、VMM resume 和内存 refault。VMM resume 本身很短，但应用第一次访问冷内存会继续产生按需缺页。

1. Wake 触发

cats shell/start/resume 或允许 wake 的 Endpoint 请求到达；同一 Cat singleflight。

2. 健康检查

确认原 Node、VMM PID、API socket、blockd、lease epoch 和 memory backing 都存在。

3. 容量准入

检查 CPU run slot、Host memory headroom 和并发 refault 预算；必要时先 Cold 其他 Cat。

4. VMM Resume

恢复时钟、Hypervisor VM、Device Manager、vCPU，顺序不能反。

5. RAM Refault

Guest Kernel/进程访问冷页时从本地 NVMe 按需读回，不全量加载 Guest RAM。

6. Ready

Guest Agent 心跳、磁盘和基础健康检查通过；清理睡眠中的旧 session。

7. Route Active

发布新 activation epoch；等待中的 shell/HTTP 请求连接 Guest。

9. Suspended/Running → Cold：彻底资源回收

Cold 的目标是让 Cat 不再依赖原 Host。进入 Cold 前必须确保远端磁盘 durable；之后退出 VMM、停止设备 backend、清理本地资源并撤销运行时 Attachment。

进入 Cold

  1. 阻止新 exec、deploy、mount 和流量激活。
  2. Running 先 Guest syncfs；Suspended 的 Guest 已冻结。
  3. 每卷强制 drain 到 remote generation == local generation。
  4. drain 失败保留 blockd、pending、lease 与源 runtime，等待重试。
  5. 成功后 Route unbound，VMM/backend 退出并释放 lease。
  6. 删除 tap、socket、cgroup、memory backing 和本地 Secret。
  7. clean cache 进入立即可淘汰队列。

Cold 唤醒

  1. Scheduler 选择任意健康 Node。
  2. 创建更高 Attachment fencing epoch。
  3. 启动空或复用 clean cache 的 cats-blockd。
  4. 建立 tap、vsock、cgroup 和 VMM 配置。
  5. 启动全新的 Cloud Hypervisor。
  6. Guest 从 RootDisk boot；ext4 journal recovery。
  7. Guest Agent Ready 后发布 route epoch。
  8. 用户进程按 image/service policy 重新启动。

9.1 VMM 退出后真正释放的内容

KVM / CPU

  • VM fd 和 vCPU fd 关闭
  • vCPU thread 消失
  • 寄存器/中断/时钟状态释放
  • CPU cgroup allocation 释放
  • 不保留 Guest process state

Memory / Device

  • Guest mmap 和 memory slots 删除
  • VMM heap/stack 释放
  • memory backing file 删除
  • virtio frontend/eventfd/socket 关闭
  • blockd 在 final FLUSH 后退出

Network / Local State

  • tap 与 per-Cat firewall 删除
  • 运行 route binding 清除
  • 本地 Secret 清除
  • dirty/pending 必须为零
  • clean disk cache 可全部淘汰
Cold 的 Ground Truth：只剩 PostgreSQL 中的 Cat/Disk/Endpoint 记录和对象存储中的 RootDisk/PersistentDisk。新 Host 不需要旧 Host 上的任何文件才能启动。

10. 为什么 V1 不把内存 Snapshot 当默认睡眠

“把内存写成 Snapshot、退出 VMM、以后 restore”理论上能同时释放 Host RAM 和保留进程，但会引入完整的 CPU/设备/网络/版本一致性问题。它应是未来第三层 Hibernate，而不是 V1 的 Suspend 或 Cold。

方案保留进程释放 VMM/RAM跨 Host复杂度与风险
Pause + Page-out是保留 VMM；大部分 RAM 可回收否最低；依赖本地 NVMe 和原 Host
Cold fresh boot否全部释放是低；只依赖成熟磁盘恢复
Hibernate Snapshot/Restore理论上是退出后可全部释放理论上是高；必须迁移 CPU、RAM、时钟、设备 backend 和网络状态

数据量

8GiB Guest 可能产生数 GiB 内存 Snapshot。即使按 dirty page/压缩优化，写入 NVMe/对象存储仍有显著延迟和成本。

设备一致性

vhost-user-blk 的 queue、in-flight request、interrupt、socket 和 cats-blockd transaction 必须与 VMM snapshot 对齐。

版本兼容

Cloud Hypervisor 不保证 Snapshot/restore 跨版本兼容。Node 滚动升级会与长期 Hibernate Snapshot 冲突。

网络语义

Guest TCP 状态恢复不代表 NAT、LB 和对端连接还存在。旧 vsock session 也必须丢弃重建。

磁盘原子点

内存 Snapshot 必须引用明确的 disk durable generation；否则 RAM 中的文件系统状态与远端盘版本不匹配。

安全

Snapshot 包含应用密钥和进程内存，必须独立加密、授权、保留和安全删除，不能当普通 cache。

决策：V1 只支持“同 Host Pause + Page-out”和“跨 Host Cold fresh boot”。Hibernate 只有在精确 Cloud Hypervisor + cats-blockd 版本完成 crash、migration、device 和安全验证后再加入。

11. 容量记账与自动分层

Suspend 的物理 RSS 很低，但它仍是一笔可恢复内存承诺和本地 NVMe 消耗。调度器不能只用当前 RSS 做 placement。

11.2 为什么会出现“逻辑 1.6TiB，物理 512GiB”

如果一个 Node 上有 200 个 8GiB Suspended Cat，它们的逻辑可恢复内存是 1.6TiB。即使当前 RSS 总和只有几十 GiB，也绝不能让 200 个 Cat 同时 resume。需要 overcommit 上限、并发唤醒限流和 Cold 降级。
水位动作目的
RAM 低压允许 Running → Suspend；正常 page-out降低闲置计算成本
RAM 高水位加速 oldest Suspended page-out；限制同时 Resume避免 Host reclaim 风暴和 OOM
NVMe memory backing 高水位把最老、低优先级 Suspended Cat 转 Cold释放真正的本地盘空间
Dirty/Pending 高水位停止新的 Suspend/Cold；先回压 Guest 写并完成提交不能删除唯一未提交数据
用户请求 Wake 无 headroom短队列；优先 Cold 其他低优先级 Cat；超时返回明确错误不能直接 resume 导致整机抖动
Node drainSuspended Cat 不能 live 搬迁，先转 Cold，再在其他 Node fresh boot解除 Host 亲和

11.3 自动策略

CATS_AUTO_WARM_AFTER_SECONDS=600，CATS_AUTO_COLD_AFTER_SECONDS=86400；设为 0 可关闭对应边界。计时来自持久化的稳定 observed state，每次晋级重新检查工作租约。
if cat.running and explicit_work_count == 0:
    suspend(cat)                        # 立即 pause + page-out

if cat.suspended and (
       state_age > warm_after
    or node.memory_pressure > high
    or node.memory_backing_pressure > high):
    warm_stop(cat)

if (cat.suspended or cat.warm) and (
       state_age > cold_after
    or node.snapshot_pressure > high
    or node.draining):
    cold_stop(cat)

if wake_requested(cat):
    if cat.state == Suspended and original_node_healthy:
        admit_resume_or_queue(cat)
    elif cat.state == Warm and original_node_healthy:
        admit_restore_or_queue(cat)
    else:
        cold_start_on_new_node(cat)

12. 故障、取消与竞态

睡醒涉及 Guest、VMM、blockd、Node 与控制面，必须把每个中间点定义成可恢复阶段。不能只保存一个布尔值 sleeping=true。

故障点正确状态恢复动作
Guest sync 超时保持 Running 或标记 SuspendFailed不强行宣称 durable；按策略重试或执行受控 Cold shutdown
本地 durability barrier 失败不进入 Suspended保留 Guest/runtime；本地 fsync/ENOSPC 恢复后重试
强制 remote drain 失败不进入 Warm/Cold，不创建 Snapshot，不 Detach/迁移保留 blockd、pending、lease 与源 runtime；对象/DB 恢复后同一 job 重试
vCPU 已 pause，Device pause 失败VM 处于 Pausing/Error优先尝试 resume 回 Running；不执行 page-out 或 cleanup
Pause 成功，Page-out 部分失败可以保持 Suspended，但记录低回收率page-out 是 best-effort；稍后重试；持续高 RSS 则转 Cold
Page-out 过程中收到 Wake相同 Cat lifecycle generation 仲裁取消后续 page-out，等待当前 syscall 返回，再 resume
VMM 在 Suspended 时崩溃进程状态丢失；不可只靠 memory file restoreFence 旧 runtime，按 Cold Recovery fresh boot
整台 Host 丢失Suspended memory 视为丢失云 fencing/Node lease 确认；新 Host 获取更高 disk epoch；Cold start
Resume 后 Guest Agent 未 ReadyResuming 超时收集 console/VMM/device 指标；一次 resume 修复失败后 Cold reboot
Cold cleanup 中控制面重试Job 幂等按明确路径和 PID identity 重做；不存在视为已清理
旧 Route cacheNode 再检查 activation epoch旧 epoch 返回 409/503，不代理到错误 Guest

禁止操作：不能在未确认磁盘 FLUSH 时删除 dirty cache；不能在旧 VMM 可能继续运行时给新 Host 发相同 Attachment epoch；不能把 page-out 失败误认为 Cold；不能仅凭控制面状态删除 Host 上未知 PID。

13.1 Node 侧伪代码

async fn suspend_cat(job: SuspendJob) -> Result<SuspendResult> {
    verify_generation_and_pid_identity(job)?;
    session_gate.block_new_sessions(job.cat_id).await?;

    guest.sync_filesystems(job.deadline).await?;
    let durable = blockd.flush_all(job.attachment_epochs).await?;

    ch.pause(job.api_socket).await?;
    verify_vmm_state(job.api_socket, "Paused").await?;

    let ranges = discover_guest_memory_mappings(job.vmm_pidfd)?;
    let before = read_memory_accounting(job.vmm_pid)?;
    let advised = process_madvise_pageout(job.vmm_pidfd, ranges)?;
    let after = wait_for_reclaim_or_deadline(job.vmm_pid, job.reclaim_target).await;

    persist_observation(Suspended {
        durable_generation: durable,
        advised_bytes: advised,
        resident_bytes: after.rss,
        backing_bytes: stat_blocks(job.memory_backing),
    }).await?;
}

async fn resume_cat(job: ResumeJob) -> Result<()> {
    verify_same_node_runtime(job)?;
    scheduler.admit_resume(job.cat_id).await?;
    verify_blockd_and_lease(job.attachment_epochs).await?;
    ch.resume(job.api_socket).await?;
    guest.wait_ready(job.deadline).await?;
    route.publish_new_activation_epoch(job.cat_id).await?;
}
权限：process_madvise 操作另一个进程需要 pidfd、ptrace 访问检查和 CAP_SYS_NICE。不要给整个 cat-agent 无限制 root；可以把 memory-reclaimer 拆成只允许操作已登记 VMM PID/range 的小型特权 helper。

15. 验收测试

需要在真实裸金属、真实 KVM、真实 cats-blockd 和真实 NVMe 上验证。只 mock Cloud Hypervisor API 无法发现 pinned page、virtqueue、时钟和 refault 问题。

正确性

  • Guest 内计数器/进程在 Suspend 后继续
  • Root/PersistentDisk digest 一致
  • fsync 文件 Host crash 后恢复
  • 未 fsync 数据允许按语义丢失
  • Guest clock 不倒退
  • 旧 session/route epoch 被拒绝

资源回收

  • pause 后 vCPU CPU≈0
  • 8GiB 多种工作集 RSS 回收率
  • memory backing 实际 block
  • pinned/hugepage 对照组
  • clean cache 淘汰与 dirty 保留
  • Cold 后 PID/fd/tap/cgroup=0

唤醒性能

  • VMM resume P50/P99
  • Guest Ready / shell ready
  • HTTP first byte
  • NVMe refault bytes/latency
  • 1/10/100 Cat 并发 Wake
  • 内存压力下 admission 行为

故障注入

  • FLUSH 各阶段 kill -9
  • vCPU pause 后 device pause 失败
  • page-out 中 wake
  • Suspended VMM crash
  • 整台 Host power off
  • 旧 Host 恢复网络尝试写

长时间稳定性

  • 72h Suspend/Resume 循环
  • memory backing 泄漏
  • fd/tap/cgroup 泄漏
  • RSS 回收退化
  • 网络连接与 DNS 恢复
  • Node drain 全流程

上线门槛

  • 无成功 FLUSH 数据丢失
  • 无双 Attachment writer
  • 无 Host OOM
  • 无 VMM/device resume hang
  • Cold 不依赖旧 Host 文件
  • 每个失败阶段可自动收敛

15.1 已有实验结论

2026-07-21 的 AWS i4i.metal 正式实验中，Suspend + page-out 的唤醒控制路径为 0.212–0.231 秒；暂停后的 VMM 物理 cgroup 内存为 6.941 / 11.635 / 17.336MiB（分别对应 512MiB / 1GiB / 2GiB Guest），回收率为 97.706%–98.508%，30/30 次恢复保持 Guest boot UUID 不变。本地 snapshot + VMM exit 的恢复控制路径为 0.380–0.399 秒。
这些数据验证了 Cloud Hypervisor 生命周期控制和 Guest RAM 回收机制；它们不是包含跨 Host 传输、远端 snapshot 下载、用户服务 readiness 和并发负载的端到端生产指标。正式结论以同目录的实验总报告和原始 CSV 为准。
