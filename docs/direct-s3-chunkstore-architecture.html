1. 结论与边界

Direct-S3（Direct-OS：Direct-ObjectStorage 接口的一种实现）ChunkStore 不是把一个 100GB raw image 上传到 S3，也不是让 Guest mount S3。它在 Host 上实现一个稀疏虚拟块设备：只把实际写过的逻辑区间保存为不可变对象，并通过一个很小的 Block Map 找到这些对象。

Direct-OS 是接口名；本文只覆盖其中的 Direct-S3 实现。

Guest 接口保持不变

Guest 只看到 /dev/vda、/dev/vdb 和标准 ext4。Guest 不安装存储客户端，不持有 S3 或 Metadata 凭证。

远端 Ground Truth 与本地待发布真相

Strict 成功 FLUSH 的 Ground Truth 已在 S3/PostgreSQL；Relaxed 的 local generation 大于 remote generation 时，本地 pending pack 是唯一权威副本，不能当作可删除 Cache。

Root 与 Lease 由强一致数据库管理

PostgreSQL 保存当前 root_hash、Generation、Lease Owner 和 Fencing Epoch；它不保存用户数据块。

FLUSH 按盘选择持久化边界

Strict 在 S3 + Root CAS 后 ACK；Relaxed 在本地 immutable pack 持久后 ACK，由有界后台 publisher 推进远端水位。完整契约见 ADR-0022。

与现有架构的关系：Cloud Hypervisor、vhost-user-blk、Guest ext4、RootDisk、PersistentDisk、MountBinding、Attachment 和 cats CLI 都不改变。只替换 cats-blockd 下方的 JuiceFS raw-file 数据路径。
不是上线承诺：本文定义正确性协议和模块边界。是否替换 JuiceFS，必须由真实 S3、真实 Cloud Hypervisor、git/package install、SQLite/fsync、故障注入和长期稳定性测试决定。

Write Cache 语义：普通 WRITE 可以在写入本地内存/NVMe 后返回，但必须向 Guest 正确声明 volatile write cache。Host 在 FLUSH 前永久损坏时，未 fsync 数据允许丢失；已经成功完成 FLUSH/FUA 的数据不允许丢失。
V1 不实现逐写 WAL：普通写不为每个 4KiB 请求追加数据库式日志。只有 FLUSH 到来时，才把屏障前的 Dirty Set 固定成不可变 Pending Commit Pack。若未来要让已 ACK 但尚未 FLUSH 的普通写也能承受整台 Host 永久丢失，需要跨 Host 复制的日志或同步远端提交；单机 NVMe WAL 仍然不够。

6.3 DISCARD / TRIM

完整 Chunk 的 DISCARD 把对应 ChunkRef 改为 Hole；部分 Chunk 的 DISCARD 记录 Zero Delta 或在 Compaction 时归零。不会同步删除 S3 对象，因为旧 Snapshot 可能仍然引用它。

7. FLUSH/FUA 提交协议

顺序必须是“本地 pack 先持久、对象先持久、Root 后发布、本地 pack 最后清理”，不能交换。每卷维护 L=local durable generation 与 R=remote durable generation，并始终满足 R ≤ L。

Strict / Relaxed：Strict 在 R 前进后 ACK；Relaxed 在 L 前进后 ACK，步骤 3–6 只由后台 publisher 执行。Relaxed 冷缓存局部 WRITE 记录精确 byte ranges，不在 Guest WRITE/FLUSH 线程同步 GET/PUT/CAS；Host 永久丢失只恢复到 R。

CAS 前崩溃

旧 Root 继续可见。已经上传的对象没有 Root 引用，经过安全等待期后由 GC 删除。

CAS 后、ACK 前崩溃

新 Root 已经是 Ground Truth。重启后根据 txn/generation 识别已提交状态，只清理 Pending Pack，不重复增加 Generation。

CAS 失败

Generation、owner 或 epoch 冲突才说明 Writer 已被 Fence。S3/DB timeout 只是可重试 publish error；Relaxed 保留本地 pack，不能直接向 ext4 注入 EIO。

延迟与风险边界：Strict FLUSH 至少包含一次 S3 PUT + Metadata CAS；Relaxed 关键路径只有本地 pack 持久化，但 Host 永久损坏会丢当时的 L-R。要同时获得本地级 fsync 与 Host-loss RPO 0，必须增加跨 Host Replicated Write Log。

正常迁移

  1. 停止 Guest 新写入。
  2. 完成最终 FLUSH，记录 final root。
  3. Host A 关闭 vhost-user backend。
  4. 释放 Lease。
  5. Host B 获取 epoch+1。
  6. 空 Cache 加载 Root，启动 Guest。

Host A 突然失联

  1. 控制面等待 Lease 到期或执行受控撤销。
  2. Host B 获取更大的 Epoch。
  3. Host A 即使恢复，也无法通过 Root CAS。
  4. Host A 上传的对象没有新 Root 引用，只会成为 Orphan。
  5. Host B 从最后一次成功 FLUSH 的 Root 恢复。
禁止行为：不能因为 S3 支持多客户端读取，就允许两个 cats-blockd 同时写同一个 ext4 Volume。两个 Writer 分别修改不同 LBA 也不安全，因为 ext4 Journal 和分配器仍然是同一个文件系统。

10. Snapshot、Clone、Restore 与 GC

Checkpoint / Snapshot

  1. 对 Active Volume 建立 Barrier。
  2. 完成一次远端 FLUSH。
  3. 把当前 root_hash + generation 写入 Snapshot Row。
  4. 解除 Barrier。

不复制 Base Chunk、Delta 或 Map Node。

Clone

  1. 新 Volume 创建新的 ID 和 Lease 状态。
  2. 初始 Root 指向同一个不可变 Map Root。
  3. 后续写入创建新的 Leaf、Root 和 Data Object。
  4. 旧对象由两个 Root 共同引用。

Restore

  1. 拒绝或冻结新写入。
  2. 完成当前写入的处理策略：提交或明确丢弃。
  3. 数据库将 Volume Root CAS 到 Snapshot Root。
  4. Generation 增加，失效本地 Clean Cache。
  5. 重新开放设备。

Mark-and-Sweep GC

  1. 以所有 Active Volume Root 和 Snapshot Root 为起点。
  2. 遍历 Root、Leaf、Base、Delta 引用。
  3. 形成 Live Object 集合。
  4. 只删除未引用且早于 Grace Period 的对象。
  5. GC 进度和删除清单必须可审计。
不能仅靠引用计数：上传对象后、Root CAS 前随时可能崩溃；Snapshot 删除、Clone 和并发 GC 也会造成引用计数时序问题。不可变对象 + 周期性 Mark-and-Sweep 更容易证明正确。

11. 小文件与写放大

10 万个 Guest 文件不会变成 10 万个 S3 对象。cats-blockd 看不到文件名，只看到 ext4 写入的 LBA。但 ext4 Journal、inode table、目录块和重复 FLUSH 会反复改写少量热区，因此完整 4MiB Chunk 上传会造成写放大。

阶段远端表示优点问题/触发条件
V1：Full Chunk每个 Dirty 逻辑 Chunk 生成新的 4MiB Base Object代码简单；读路径简单；容易验证崩溃一致性4KiB 写也可能上传 4MiB；只适合功能验证和初期小规模。
V2：Delta Pack一次 FLUSH 将多个 64KiB Dirty Page 打包成一个 Segment减少 PUT 数和传输字节；适合 ext4 Journal 和 Git 小文件读时需要 Base + Delta 合并；Map 保存 segment offset/length。
Compaction后台把 Base + 多个 Delta 合并为新 Base限制读放大和 Delta Chain 长度建议在 delta_count > 4、delta_bytes > 50% base 或 Chunk 变热时触发。

12. 租户隔离、凭证与加密

权限边界

  • Guest 永远拿不到 S3/DB 凭证。
  • cat-agent 只给 blockd 发送短期 Volume Token。
  • Token 限定 tenant、volume、attachment、epoch 和操作。
  • blockd 使用节点身份换取短期远端凭证。

对象加密

  • 每个 Volume 独立 DEK。
  • DEK 由平台 KMS KEK 包装。
  • 对象 Header 作为 AEAD Associated Data。
  • Map 中保存 key_version。
  • 后台重写完成密钥轮换。

完整性

  • 上传提供服务端 checksum。
  • Map 保存明文或规范编码 Hash。
  • 下载后再次验证。
  • 校验失败不写入 Clean Cache。
  • 错误进入只读/故障状态并告警。
第一版不做跨租户去重：跨租户内容寻址可能泄露“另一个租户是否拥有某段数据”，并让密钥轮换、引用追踪和删除证明复杂化。Volume 内通过不可变 Root 复用未修改对象已经能获得主要 CoW 收益。

13. 故障处理矩阵

故障正确行为不能发生恢复动作
blockd 进程崩溃同 Host 从 pending pack 重建 L；旧 Root 完整attach 恢复阶段先做远端写或跳过 ACK pack先恢复本地队列，再由 publisher 按 generation 幂等重放。
Host 永久损坏Strict 从成功 FLUSH 恢复；Relaxed 从 R 恢复把 publisher 定时器当作真实 RPO新 Host 获取更高 Epoch；以故障时 L-R 的 age/bytes/generations 记账。
S3 PUT 超时Strict 等待/失败；Relaxed 本地 ACK 后后台重试将普通 timeout 当 fencing 或向 Relaxed ext4 注入 EIO保留 pack 和 lease；记录 publish error；远端恢复后继续。
S3 返回损坏数据Checksum 失败，拒绝将数据交给 Guest把损坏内容写入 Cache 后继续运行重试、读取其他副本/区域；无法恢复时 Volume 进入 Faulted。
PostgreSQL 不可用Strict 等待/失败；Relaxed 本地推进到配额水位绕过 CAS 或让本地队列无界增长有界队列/deadline；只剩 pin 数据时背压；恢复后重连。
Lease expiry lapseowner/epoch 未变时继续 renew/publish因瞬时抖动自我 fence竞争 acquire/revoke 增加 epoch 后旧 Writer 才 fail closed。
强制 lifecycle drain 失败不越过 Stop/Warm/Snapshot/Detach/迁移边界释放 lease、删除 pending 或宣称 Cold保留源 runtime；控制器重试到 R == L。
GC 进程崩溃最多延迟空间回收删除任何仍被 Root/Snapshot 引用的对象GC Job 使用 epoch、checkpoint 和幂等 delete，重新扫描。
Compaction 崩溃旧 Base + Delta 仍可读先删除旧对象再发布新 Map新 Base 成为 Orphan 或在重试时复用；Root CAS 后才允许旧对象进入 GC。

15. 实施计划

不建议一次性删除 JuiceFS。先让同一套 Block Engine 支持多个 Backend，保持可对照、可回退。

阶段实现内容退出条件
P0：已有 DemoPython/NBD、固定 Chunk、Generation Manifest、原子 HEAD、真实 JuiceFS 对照、崩溃注入已完成：冷恢复、HEAD 前后崩溃和兼容 ext4 验证通过。
P1：接口拆分BlockEngine、LocalCache、BlobStore、MetadataStore 四个边界；File/JuiceFS/S3 三种 BlobStore相同测试套件在 File 和 JuiceFS Backend 上通过。
P2：Rust 正确性版本4MiB Full Chunk、两级 Map、PostgreSQL CAS、Lease/Fencing、S3 checksumNBD/ublk 下 ext4、fsck、fio、kill -9 和 stale-writer 测试通过。
P3：虚拟化接入vhost-user-blk、多队列、Cloud Hypervisor 动态磁盘、RootDisk boot真实 Guest 中系统盘和 PersistentDisk 生命周期通过。
P4：空间与小写优化Delta Pack、Compaction、TRIM、Snapshot/Clone、Mark-and-Sweep GCgit clone、apt/npm、SQLite fsync 的远端写放大和延迟达到阈值。
P5：生产强化KMS、Credential Broker、限流、配额、审计、在线升级、跨 AZ 恢复、容量计划故障演练、72h soak、升级回滚、数据恢复 Runbook 通过评审。
P6：灰度决策同一产品 API 下按 Volume 选择 JuiceFS 或 Direct-S3 Backend（Direct-OS 实现）小比例 RootDisk → PersistentDisk；出现错误可 Detach 并切回兼容 Backend。
 
trait BlobStore {
    async fn put_immutable(object_id, bytes, checksum) -> PutResult;
    async fn get(object_id, range) -> Bytes;
    async fn head(object_id) -> ObjectMetadata;

}

16. 验收与故障注入

正确性

  • ext4 mkfs、mount、unmount、journal replay
  • tree digest 冷恢复一致
  • fsck.ext4 强制检查
  • fio verify、fsx、随机断电点
  • TRIM 后读取全零
  • Snapshot/Restore/Clone 内容一致

故障注入

  • 双水位各阶段 kill -9
  • lease expiry lapse、竞争 acquire/revoke
  • S3/DB 延迟、5xx、超时、failover
  • Relaxed 配额、淘汰与背压
  • 强制 drain 失败时保留源并重试
  • 旧 Host 恢复后 stale epoch 发布

工作负载

  • 100GiB / 100,000 小文件
  • git clone、checkout、gc
  • apt、npm、pip install
  • SQLite WAL + 每事务 fsync
  • PostgreSQL/MySQL 开发实例
  • Docker/OCI layer 解包

必须记录

  • 远端上传/下载字节
  • S3 GET/PUT 数和费用模型
  • Full Chunk 与 Delta 写放大
  • Strict/Relaxed FLUSH P50/P99
  • L-R generations/bytes/oldest age
  • publisher throughput 与配额背压
上线阻断条件：Strict 成功 FLUSH 在删除 Host 后无法恢复；Relaxed 未暴露实际 L-R，或 drain 失败仍删除唯一的本地副本；旧 Fencing Epoch 能发布 Root；或没有明确的每卷 pending/local 物理上限。每卷上限不等于 Host 全局容量证明。

Direct-S3 替换 JuiceFS 的决策门

比较项Direct-S3（Direct-OS 实现）必须证明
正确性FLUSH、FUA、TRIM、Snapshot、Fencing 和恢复语义至少与 JuiceFS 方案相同。
延迟Cache Hit 不因自研 Map 明显回退；FLUSH 延迟达到产品可接受范围。
成本S3 请求费、写放大、Compaction 和 GC 后的总成本低于 JuiceFS 双层映射方案。
运维能够定位某个 LBA 对应的 Root、Map、Data、Delta、Checksum 和提交事务。
恢复有可执行的 Volume Verify、Read-only Attach、Export Raw、Rebuild Cache 和灾难恢复工具。
