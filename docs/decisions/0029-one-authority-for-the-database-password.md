# ADR-0029：数据库口令只有一个权威

- 状态：Proposed
- 日期：2026-08-05
- 范围：PostgreSQL 口令的来源与消费方式、托管轮换的存废、凭据故障的探测、以及发布前的连通性闸门。
- 不含：连接数上限与池化（#76）、RDS Proxy 与 IAM 数据库认证的评估、控制面资源库迁移（P0-A）。

## 背景

2026-08-04 的事故不是「有人忘了改一处口令」，而是这套系统**没有权威**：RDS 开着托管
主口令轮换，而每一个消费方各自持有一份写死的拷贝，没有任何一方消费那个权威。轮换发生
时，所有凭据同时失效，且**没有任何东西察觉**。

PostgreSQL 只在 connect 时认证，所以症状是延迟且伪装的：已建立的连接照常服务十三个
小时，只有新连接失败。表现出来是「创建 Cat 失败」，而不是「数据库不可达」——那看起来
像组件 bug，不像凭据问题。因为每个 Cat 各持一条连接（#76），它更进一步伪装成连接耗尽，
于是有人停掉 `cats-worker` 去「释放连接」，杀死十二个健康 Guest，而重启恰恰需要新连接。
一次部分故障就此变成全面故障。

修复过程中查明了五条独立的传播路径，每一条都足以单独造成这次事故：

1. **noded 的环境冻结在启动那一刻。** `cats-noded` 启动时读一次 `CATS_POSTGRES_URL`，
   而每个 `cats-blockd` 通过 `Command` 继承它——spawn 时只 `env_remove("CATS_CRASH_POINT")`
   （[`node-agent/src/runtime/blockd_control.rs`](../../node-agent/src/runtime/blockd_control.rs)）。
   轮换之后，一个启动于轮换前的 worker 会**无限期地**用旧口令 spawn 子进程，不重启、
   不报错。这就是「新建 Cat 失败、在跑的 Cat 没事」的完整机制。
2. **重连复用被捕获的 DSN。** 两个 adapter 的 worker 线程把 DSN 字符串抄进闭包，
   `client.is_closed()` 触发的每一次重连都重新出示同一个已失效的口令。活着的进程
   永远回不去，而「重启一下」正是陈旧凭据做不到的事。
3. **usage adapter 根本不重连。** 它的 worker 循环没有任何 `is_closed()` 检查，一次断连
   就让后续每个作业都跑在死连接上。这一条与轮换无关，任何网络抖动都触发。
4. **发布把旧口令传下去。** 部署流程从**存活的** k8s Secret 读出口令再交回 Terraform，
   于是每次发布都把当时那份口令原样复制一遍。这就是为什么「一次部署等于一次重启」会把
   轮换变成全面故障。平台栈自己的 output 注释早就写明了相反的意图。
5. **探测器不存在，且没有收件人。** RDS 的错误日志没有导出到 CloudWatch，所以那句
   `FATAL: password authentication failed` 从未离开实例；而账号里既有的三个告警
   `alarm_sns_topic_arns = []`，一直在对空气报警。

## 决定

### 1. 权威只有一个，托管轮换保持开启

RDS 的 `MasterUserSecret` 是数据库口令的唯一权威。**不关闭托管轮换**——关掉它只是把
「口令会在无人知晓时改变」换成「口令永远不改变」，用一个更差的安全姿态去迁就一个消费
方缺陷。正确的方向是让消费方消费权威。

推论：任何组件都不得把口令写进自己的配置作为长期事实。写下来的只能是**指向权威的引用**
（secret ARN）加上不会轮换的部分（user / host / port / database / sslmode）。

### 2. 消费方在连接时解析，不在启动时冻结

DSN 由文件提供，adapter 在**每一次** connect——首连与每一次重连——重读该文件
（`DsnSource::File`，已在 #92 实现）。这条把第 1、2 条传播路径一起关掉，且不需要 adapter
知道 Secrets Manager 是什么：provider 相关的部分留在平台层，符合 ADR-0005 的分层。

### 3. 每个平台用自己的原生机制让那份拷贝跟随权威

| 平台 | 机制 | 状态 |
|---|---|---|
| metal worker | systemd `ExecStartPre` + 15 分钟 timer 渲染 `/run/cats/postgres-url` | 已实现（#93） |
| 发布流程 | 从 `MasterUserSecret` 组装 DSN，不再回读存活 Secret | 已实现（#97） |
| Kubernetes | 见下节 | **本 ADR 决定** |

### 4. 集群内的刷新与发布前的连通性验证，是同一个机制

这两件事此前被当作两个待办，但它们的约束指向同一个实现：

- 刷新任务必须在集群内运行（要 patch Secret），且**应当**在写之前先验证组装出的 DSN
  真的能连上——否则它最坏的失败模式是安静地写进一个错误的口令，等下一次重启才炸。
- 连通性验证**只能**在集群内运行：实例 `publicly_accessible = false`，入站只按安全组
  引用放行，GitHub 托管的 runner 连不到它。

所以定义**一个** in-cluster 任务，三步且顺序不可换：

```
读取 MasterUserSecret → 组装 DSN → 连接 PostgreSQL 验证 → 仅在成功后 patch Secret
```

它以两种方式运行，同一份代码：

- **CronJob**，周期性执行。覆盖「两次发布之间轮换、随后 Pod 意外重启（OOM / 驱逐 /
  节点排空）」这个场景——那是 #97 关不掉的唯一剩余场景。
- **发布闸门**，部署流程在替换 Pod 之前运行它一次并等待结果，紧挨既有的 schema 版本
  闸门。轮换从此不会再靠「把生产打挂」被发现。

镜像在本仓库构建并按摘要固定（与 ADR-0024 一致），不在运行时从未固定的公共 registry
拉取。AWS 身份用 EKS Pod Identity，与 usage 流水线现有的做法相同；RBAC 收窄到
`cats` 命名空间内那一个 Secret 的 `get`/`patch`。

**明确否决的替代方案：**

- **init container 在 Pod 启动时渲染。** 这会把 Secrets Manager 放进控制面的**存活路径**：
  Secrets Manager 短暂不可用时 Pod 根本起不来，把一次外围抖动升级成一次停机。可靠性
  边界文档明确禁止外围依赖进入已有 runtime 的存活路径。
- **EventBridge 接轮换事件 → Lambda。** 需要 Lambda 进 VPC 并持有 EKS API 凭据，比
  CronJob 多一整层，换来的只是延迟从「一个周期」降到「近实时」——而 #91 的告警已经把
  未覆盖窗口的**发现**时间压到分钟级。
- **在 adapter 里直接调用 Secrets Manager。** 会把 AWS SDK 拉进 provider-neutral 的存储
  端口后面，违反 ADR-0005，并让本地开发与非 AWS 部署凭空多一个依赖。

### 5. 探测器必须有已确认的接收方

RDS 错误日志导出到 CloudWatch，metric filter 匹配 `password authentication failed`，
告警阈值 0（对这台实例而言，被拒绝的凭据没有良性稳态）。`alarm_action_arns` 是**必填且
校验非空**的模块输入，不是带默认值的可选项——一个不通知任何人的告警不是探测器，而账号
里已经有三个处于那个状态。

「已确认」是字面意思：Terraform 会把**未确认**的邮件订阅报告为已创建。上线时必须实际
发一条消息证明送达。（本次上线中，确认邮件落进了垃圾箱——这正是「建好了」与「送得到」
之间的距离。）

## 不变的契约

- Guest 永远不接触 PostgreSQL 凭据；本 ADR 的任何机制都不把凭据带进 Guest 或 NodeJob。
- 刷新任务不得成为存活路径。它失败的后果是「拷贝保持陈旧」——也就是今天的状态——由
  告警发现；**绝不允许**因为刷新失败而重启、驱逐或杀死任何正在运行的东西。
- 发布闸门必须 fail closed：验证失败就不替换 Pod，而不是记一条警告继续。
- 旧 attachment epoch 的 fail-closed 语义与本 ADR 无关，不得因凭据机制变化而放宽。
- 口令绝不出现在错误消息、日志、Pod spec、命令行参数或 Terraform state 中。关于 DSN
  文件的报错只允许指出路径。

## 后果

**得到：** 轮换不再需要人参与；「轮换 → 发布 → 全面故障」这条链断开；连通性验证终于有
了一个能运行的位置，而且是免费搭在刷新任务上的；两个待办收敛成一个机制，只需维护一份
代码和一个镜像。

**代价：** 集群内多一个工作负载和一个自建镜像；多一套 Pod Identity 与 RBAC；每次发布多
一步、多约半分钟。

**新风险：** 闸门本身成为发布的阻塞点。缓解方式是把两种运行模式的失败语义分开——
CronJob 失败只告警不阻塞任何东西，只有发布闸门那一次失败才阻塞发布。

## 分阶段实施

顺序是按「写错了会怎样」排的，不是按工作量。

1. **镜像与任务逻辑**，先以手工方式在集群内跑一次，验证 Pod Identity、RBAC 与到 RDS 的
   网络可达性。
2. **CronJob，只读模式**：完整执行读取、组装、连接验证，但**不 patch**，只报告判断结果。
   先证明它的判断是对的，再给它写权限。这一阶段能独立发现「组装逻辑错误」而不会伤到
   任何东西。
3. **打开 patch。** 此时它已经在真实环境里判断正确若干个周期。
4. **接入发布闸门**，紧挨 schema 版本检查。

每一阶段的验收都必须包含一次**真实的失败**：故意提供一个错误口令，确认任务拒绝 patch
（阶段 2–3）、确认发布被挡下且 Pod 未被替换（阶段 4）。这套机制的全部价值在于它在错误
发生时真的会拦住，而那只能靠制造一次错误来证明。
