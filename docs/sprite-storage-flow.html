Git 操作的是本地 ext4。变化先被 page cache 与 NVMe 吸收，再由高度改造的 JuiceFS 存储层，把实际变化的磁盘块持久化为对象 chunk。

一句话答案 上传的是脏 chunk，不是整块 NVMe。

SQLite + Litestream 保存“逻辑块 → chunk”的地图；对象存储保存可恢复的数据本体。

01

不是一文件一对象

Git 创建的文件先变成 ext4 数据块、inode 与目录项。对象存储层看到的是 chunk，不是 README.md 这样的文件名。

02

不是上传整盘

100GB 是稀疏上限。系统只持久化实际变化的块；未分配空间、未变化的 base 与已有缓存无需重新上传。

03

两条异步路径

文件块成为 data chunks；块映射成为 SQLite/LTX。两者最终都进入对象存储，但 Fly 未公开它们的原子提交细节。

One file, four representations

一个文件，在四层里长得完全不同。

这也是为什么“10 万小文件”不能直接等价为“10 万次 S3 PUT”。

Git 视角

src/main.c，通过 open/write/rename 等 POSIX 操作创建。Git 的 HTTPS、SSH 或 file:// 传输协议与底层持久化无关。

ext4 视角

数据 block + inode + directory entry + allocation bitmap。小文件也可能消耗一个或多个块，因此有空间放大。

JuiceFS 层视角

哪些逻辑块变脏，以及它们对应哪些 immutable chunk。公开资料没有披露 chunk 大小与聚合算法。

对象存储视角

没有“文件目录”；只有 data chunk 对象和 block-map 的 LTX 对象。恢复时依靠映射重新拼出同一块 ext4 磁盘。
