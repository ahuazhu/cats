Cats 设计提案 · 可休眠负载

让真实应用能睡

Cat 睡觉是为了省钱。但把一个真实应用放进会自己睡觉的机器里，它会以十种方式坏掉—— 而"定时任务不跑了"只是其中两种。这份方案划一条线：平台只报事实，应用做判断。

状态 设计提案，未实现 日期 2026-07-27 服从 ADR-0002 · ADR-0007

问题十种坏法，只有两种和定时任务有关

这些是把一个真实的 agent 类负载迁进 microVM 沙箱之后实际遇到的问题，不是设想出来的清单。

症状表现
定时任务静默停止进程内的 @Scheduled / setInterval / time.Ticker 到点不触发
定时任务醒来暴走一次唤醒补跑几十次，重复写库、重复调外部 API
应用永远睡不着应用自己的健康检查或后台 tick 被算成"有工作"，账单按全价走
被冻在一次 IO 中间后台任务写文件写到一半机器睡了，醒来是半截数据
看门狗杀健康的进程睡醒后心跳当然是旧的，看门狗以为进程卡死，把它重启
凭据在睡眠期间过期醒来第一个请求就 401
挂载与连接池失效对端早已超时释放，应用以为自己还持有
慢启动被冻在半路冷启动要几分钟，期间平台看不到任何"工作"，中途睡下并卡死
日志管道断裂应用输出用的管道跨睡眠断开
Cold 之后进程不再存在没有任何东西负责把用户的常驻进程重新拉起来
Warm 之后墙钟静默错误时钟被冻在快照那一刻且逐次累加；日志时间戳、TLS 有效期、JWT exp 全部受影响

十一条里只有前两条是"定时任务"问题。所以这不是一个定时任务功能，而是一套责任划分。

原则平台报事实，应用做判断

平台知道两件应用不可能知道的事：现在几点；以及你刚睡了多久、错过了哪些时刻。

应用知道一件平台不可能知道的事：打断这段工作，有没有人要善后。

上面十个坑，全部来自有人越过了这条线。平台去猜应用忙不忙——猜宽了永远不睡，猜紧了冻在半路。 应用假设自己一直醒着——醒来发现凭据过期、看门狗要杀自己、挂载失效。

下面五层，各自解决一组症状。

第 0 层 · 前置

Service 定义：Cold 之后由谁启动进程

解决：Cold 之后进程不再存在。

Cat 降到 Cold，Guest 里的进程随虚拟机一起消失。cats exec 起的东西断连即死； setsid、nohup、tmux -d 都活不过平台侧的清理。 所以需要一个由平台记住、每次开机执行的命令定义： 

cats service set order-sync --cmd '/usr/bin/java -jar /app/order-sync.jar'

Guest Agent 每次开机启动它，崩溃后重启它。就这些。 刻意不做依赖顺序、就绪探针、重启退避策略——那些属于应用编排，不属于沙箱。

为什么必须在平台侧：只有平台知道"进程消失了"这件事发生过。 Guest 里在那一刻没有任何东西是活着的。这一层不补，后面几层都是空中楼阁。

第 1 层 · 核心

两种"我在忙"

解决：应用永远睡不着；被冻在一次 IO 中间。

现有的工作租约是一个平铺的并集——任何未过期的租约都压住休眠。这让每一个后台周期任务 都面临两难：

  • 老实申报 → 每分钟的清理任务每分钟重新压住休眠 → 这个 Cat 永远不会自动睡
  • 不申报 → 它随时可能被冻在写文件的中间 → 半截数据

两条路都是坑。根因是"我在忙"这一个词被用来表达了两种不同的意思。拆开：

模式语义典型用途
pin 我能把 Cat 唤醒，并且按住它不许睡 用户在等的响应；必须投递的消息；正在处理的请求
drain 我不唤醒 Cat。但如果它此刻正醒着，让我跑完再睡。 清理临时文件、驱逐空闲缓存、上报指标

drain 必须带预算上限（默认 60 秒）。超过预算后工作继续跑，但失去冻结保护—— 这是刻意的降级而非错误，否则一个卡死的后台 tick 能把 Cat 永久钉在 Running。

给用户的判断规则只有一句话

打断它，有没有人要善后？
有 → pin。没有 → drain。

try (var w = Cats.pin("sync-orders")) {              // 客户看得见的工作
    syncOrders();
}

try (var w = Cats.drain("clean-temp", ofSeconds(30))) {  // 家务
    cleanTempFiles();
}

落地形态：WorkKind 保持不变（它表达工作来源），新增一个正交字段表达 保活语义。判定规则相应修改：pin 的并集为空即可尝试休眠； drain 不参与"是否可以睡"的判定，只推迟已判定的休眠动作，且不超过预算。 默认 pin，所以不关心这件事的用户完全无感。

第 2 层 · 廉价高回报

睡了多久

解决：看门狗杀健康进程；凭据过期；挂载与连接池失效；日志管道断裂。

应用醒来时唯一缺的信息是"我刚才不在了多久"。给它这个数，上面四条它自己就能处理； 不给，每个应用都要自己发明一套"我是被冻住了还是我卡死了"的启发式判断。

三个档位，任选：

  • 零改动——/etc/cats/on-resume.d/ 目录，Guest Agent 在 resume 后按序执行其中的脚本
  • 一行改动——长轮询 GET /v1/resume-events
  • 契约文字——resume 之后，缓存的 token、连接池、DNS 结果、任何由本地时钟推导出的 deadline，一律视为可疑
{ "slept_ms": 7200000, "from_state": "warm", "resumed_at_unix_ms": 1785146271000 }

slept_ms 比"我醒了"这个信号有用得多，因为它一个数就分出三种处置： 睡了 3 秒什么都不用做；睡了 2 小时 token 肯定过期要重拉、连接池全部作废； 睡了 2 小时心跳当然是旧的、看门狗不要杀应用。

第 3 层 · 功能

时刻表：只叫醒，加一份"错过清单"

解决：定时任务静默停止；醒来暴走；慢启动被冻在半路。

平台承诺什么

一句话：「你会在这些时刻是运行着的。」

不携带信息，不调用应用的任何入口。唤醒时平台持有一个短的交接租约—— 只够应用建立自己的 pin。交接完成后保活权威转移给应用。

这个交接租约同时解决"慢启动被冻在半路"：它覆盖的是唤醒到应用接过接力棒之间的空白， 而不是任务时长。

为什么不做"平台调用你的任务"：那需要平台维护任务名字空间、完成检测、超时、 重试，一步步长成一个作业调度系统。而且它做不到——一次生成式的 agent turn 不可能用一个 HTTP 请求的时长来建模，请求早晚被某一层超时砍断，连带砍掉保活。

关键约束：能否"自己察觉"是分状态的

这一点由实测决定，直接影响本层的必要性：

从哪个状态醒来guest 的三个时钟能否自己发现错过了 deadline
Suspended照走，误差 0.07%能，恢复后约 2 毫秒内察觉
Warm全部冻结——静置 120 秒，三个时钟一秒都没走不能，它认为一秒都没过去
Cold全新进程，单调钟从零开始不能，没有任何记忆

而自动分层是 Suspended 稳定 10 分钟即降 Warm——所以 任何周期超过约 10 分钟的定时任务，醒来时都在 Warm 或 Cold， 恰好是应用无法自我察觉的两档。

所以错过清单不是便利功能，而是承重结构。

只有周期短于 10 分钟的任务能靠自己察觉，其余全部依赖平台把信息送达。 同理 wake_lead_ms 只对 Suspended 有意义——Warm 下 guest 根本不会察觉，提前多久都一样。

Warm 还要额外补一次校时

Warm 之后 guest 的墙钟落后真实时间（实测：静置 120 秒 → 落后 120.9 秒），而且逐次累加。 NTP 救不了：即使 guest 里跑 chrony 把 CLOCK_REALTIME 步进回来， CLOCK_MONOTONIC 也不会被修正，而后者才是所有运行时定时器 deadline 用的时钟。

所以 Warm restore 之后平台必须把时钟推进到当前墙钟。CH 源码里有一个 ClockRestoreMode::SnapshotRestore（注释就是 "advance to current wall time"）， 但实测没有生效——尚未查清是没被 vm.restore 触发、需要额外标志、还是 CH 缺陷。 这决定工作量是"触发已有机制"还是"自己补一次 KVM_SET_CLOCK"。

时刻表从哪里来

来源用户改动说明
crontab / systemd timer无 Guest Agent 只读地解析磁盘文件。注意默认 Cats 镜像里 systemd 不是 PID 1、也没装 cron，所以这条路只对自己装了 cron 的用户有效
应用上报一个依赖框架适配器枚举已声明的定时任务后上报（第 4 层）
显式声明一条命令cats schedule create worker --cron "*/10 * * * *"

应用问"我错过了什么"

这是这一层的关键。应用在启动或 resume 之后问一句：

GET  /v1/schedules/missed
→ [ { "name": "sync-orders", "missed_count": 143, "reason": "cold" } ]

POST /v1/schedules/missed/ack   { "name": "sync-orders" }

平台只报事实：这些时刻我叫醒过（或本该叫醒），你还没确认。 应用自己决定怎么办——因为只有应用知道错过一次要不要紧， 这和第 1 层的 pin/drain 是同一个判断。

两个直接好处：

  • 平台侧不需要"错过补偿策略"配置项。平台不做这个决定，所以没有 skip / 补一次 / 全补 这类需要用户理解的旋钮。
  • 它给了应用处理补跑暴发的机会。Java 的 fixedRate 在唤醒瞬间会把 错过的每一轮都补跑一遍（实测：暂停 240 秒、周期 20 秒 → 12 次执行挤在 10.6 毫秒内； fixedDelay 和 cron 不会）。平台管不了 JVM 内部的补跑， 但应用看到"错过 143 次"之后可以选择只跑一次。

时区与夏令时：一旦平台拥有 cron 表达式，它就拥有了夏令时正确性。 每条时刻表存自己的时区；0 2 * * * 在春季跳钟那天该跑零次、一次还是两次， 必须写进文档，不能依赖 cron 库的默认行为。

第 4 层 · 铺开

框架适配器：把不可约的判断变成可见的清单

解决：降低第 1 层那个分类判断的成本——但不消除它。

各生态的调度框架都存着一张已声明任务的登记表可以枚举，而且大多提供了正式的中间件或 监听器机制可以在执行前后插入代码：

生态枚举时刻表执行前后插一脚
Java / SpringScheduledTaskHolder自定义 TaskScheduler
Python / APSchedulerget_jobs()add_listener
Python / Celery beatbeat_scheduletask_prerun / postrun 信号
Go / robfig/cronEntries()cron.WithChain(JobWrapper)
Node / NestJSSchedulerRegistry拦截器
.NET / Quartzjob 列表IJobListener

所以适配器能自动做到：上报时刻表、为每个任务套上保活模式、在启动或 resume 后查询错过清单。

它不能自动做到的是分类。@Scheduled(每10分钟) 说明了 什么时候，没有说明打断了要不要紧。而默认值只能是 drain—— 否则每分钟的任务每分钟重新压住休眠——可 drain 恰好对最重要的那类工作是错的。

因此适配器的正确行为是：默认 drain，并在启动时把完整清单打印出来：

[cats] 已上报 12 个定时任务，默认按"可打断"处理：
  syncOrders        每 10 分钟   ← 打断有后果的话请标注 @CatsPin
  refreshToken      每 50 分钟   ← 打断有后果的话请标注 @CatsPin
  cleanTempFiles    每  1 分钟
  ...

把不可约的工作量变成一张开发第一天就看得见的清单，而不是三个月后的一次事故。

覆盖边界：以上都要求应用使用了调度库。手写的循环 （for { <-ticker.C; work() }、while True: sleep(600)、 setInterval(fn, 600000)）既没有登记表可枚举，也没有函数边界可包—— 这类工作只能由应用自己调用租约 API。这与语言无关。

走一遍一个订单同步服务

Spring Boot，一个每 10 分钟同步订单的任务（客户看得见）、一个每分钟清临时文件的任务、 一个对外 HTTP API、一个每小时过期的第三方 token。

用户需要做的全部事情

@Scheduled(fixedRate = 600_000)
public void syncOrders() { ... }

@Scheduled(fixedRate = 60_000)            // 不标注 = 家务 = drain

边界明确不做的

这条线会被持续推——一旦有了时刻表，用户马上会要重试、执行历史、失败告警、 "立刻运行一次"、暂停恢复、补跑历史区间。建议一次钉死：

  • ✕不做作业队列没有 fan-out、worker 池、优先级。一条时刻表对应一次唤醒。
  • ✕不做重试退避策略引擎唤醒尝试记在 operations 表里，重试语义交给幂等契约。
  • ✕不做执行历史与产物存储应用自己的日志里有。
  • ✕不做依赖编排没有 DAG，没有上下游。
  • ✕不承诺 exactly-once契约必须写明"你的任务需要幂等"。
  • ✕不做进程管理器只有"这条命令应该在跑"，没有依赖顺序和就绪探针。

能保持这么小的唯一原因：任务的实际执行完全留在应用里。

顺序内容为什么在这个位置
0Service 定义不补这个，Cold 之后一切归零

时钟语义已测完，结论已并入第 3 层

Suspended / Warm / Cold 三档均已实测（experiments/suspend-clock-semantics-20260727）。 两条对设计有决定性影响的结论：错过清单是承重结构； Warm restore 之后必须补校时。

剩下一个待查项（不阻塞第 0–2 层，只阻塞第 3 层的实现细节）： CH 的 ClockRestoreMode::SnapshotRestore 为什么没有推进时钟。 查清它决定 Warm 校时是"触发 CH 已有机制"还是"Cats 自己补一次"。

总表责任划分

事项归谁理由
Cold 之后启动进程平台只有平台知道"进程消失过"
两种保活语义 + 预算平台每个应用都会遇到同一个两难，做错就是那两个经典失败
唤醒到应用接手之间的交接平台那段时间应用还没准备好为自己说话
时刻表与到点唤醒平台应用睡着时不可能给自己定闹钟
睡了多久、错过了什么平台Guest 在空白期没有任何东西在运行
Warm restore 后推进时钟平台实测 Warm 冻住全部三个时钟且漂移累加；guest 侧无法自救
时区与夏令时正确性平台拥有 cron 表达式就拥有这个责任
把每段工作分类为 pin / drain应用不可约——关于业务语义的判断，平台无从得知
错过之后要不要补、补几次应用同上
任务幂等应用平台不承诺 exactly-once
resume 后重建凭据、连接、挂载应用平台只能提供 slept_ms 这个输入
跨 Cold 存活的业务状态应用属业务域；平台不做作业队列

这个方案不消除工作量，它把工作量放到唯一有能力承担它的一侧。应用仍然要逐处判断 "打断这段工作要不要紧"——这是不可约的。平台要做的是三件事，一件都不能少： 给出对的词汇（两种"我在忙"，而不是一种）、 给出只有它知道的事实（睡了多久、错过了什么）、 兜住应用不可能兜住的场景（Cold 之后把进程拉起来）。
